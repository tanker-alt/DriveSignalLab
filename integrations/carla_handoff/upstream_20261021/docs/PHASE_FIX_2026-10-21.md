# 相位不一致：原因、修复与验证

## 已确认根因

车辆生成器在固定相位控制器已经运行后调用 tm.set_random_device_seed(args.seed)。
CARLA 的这个接口除了设置随机种子，还执行 ResetAllTrafficLights：它重置全图灯色。
因此“生成器没有直接调用 set_state”不能证明它不影响信号。

证据：本地 LibCarla 源码 Plugins/carlaviz/backend/third_party/LibCarla/source/carla/trafficmanager/
TrafficManagerLocal.cpp 的 SetRandomDeviceSeed 调用 ResetAllTrafficLights；在实际运行的
CARLA 客户端/服务器 0.9.15 上做空场实验再次确认：

| 灯 | 设置种子之前 | 设置种子之后 |
| --- | --- | --- |
| 2401 | Yellow | Red |
| 2404 | Red | Green |
| 2402、2403 | Red | Red |

这与 111836Z 的 frame 29183–29200 完全一致。固定控制器仅在阶段边界写灯，
因此重置后的错误灯色可以持续到下一次写灯；本轮为 18 帧，而非单帧缓存误差。
探针前确认世界异步且无车辆；结束后恢复保存的灯状态/配时及世界设置，不宣称恢复精确已用相位时间。

另发现 set_state 是异步 RPC，get_state 读取客户端最近快照；写入后立即读取不能证明新状态生效。
旧相位低频日志会显示上一个快照的灯色。历史两条孤立首帧异常不能仅凭旧日志唯一归因，
因此同时完善了写入顺序与下一帧回读验证，而不把所有历史异常都断言为同一来源。

## 修改

1. 生成器删除 TM 重新播种；--seed 只控制 Python 车队规划，清单记录作用范围。
2. 控制器增加 --tm-seed=17，在接管目标信号和采集之前初始化 TM。
   设置种子仍会重置自动信号周期，但发生在实验调度开始前；不在运行中执行，不使用全图冻结。
3. 阶段写灯后调用 client.apply_batch_sync([], False) 等待服务器 RPC 处理，不额外推进仿真。
   屏障不是物理执行回执，仍必须下一帧验证。
4. 每帧实际灯色与计划比对；signal_checks.jsonl 保存期望、实际和差异 ID。
   phases.csv 增加 signal_consistency/signal_mismatch_ids。发现差异先记录异常帧，再抛错停止实验并清理。
5. 低频日志 pole_states 改名 pole_states_before_tick，避免将推进前缓存误读为执行结果。
6. controller_config.json 保存 TM 种子、配时、同步屏障和异常策略。

## 验证结果

- 56 项离线测试通过，包含黄灯/全红匹配及“异常帧先记录、停止后不再 tick”的回归测试。
- 空场快速切灯：evaluation/outputs/20261021T112833Z_620338ef，3 周期，220 帧，
  status=completed，缺帧 0，逐帧不一致 0。
- 原始触发流程：evaluation/outputs/signal_fix_validation_20261021T112910Z/
  20261021T112917Z_2debf085。控制器已运行后启动生成器，24 辆混合车型 14/5/4/1，
  车辆运行设定 20 仿真秒，控制器完成 3 个正常配时周期；4120 帧、10027 条车辆记录，
  status=completed，缺帧 0，逐帧不一致 0。
- 两次均另行读取 signals.csv 对比逐帧期望灯色，结果同样为零差异，不只相信校验器汇总。
- 车队清单 completed；清理有部分 actor 已不存在的返回，但最终核验 24 辆所属车均移除。
  在线复查车辆数为 0，世界 synchronous_mode=False。

本次没有改写旧实验。在线验证覆盖当前地图、当前 CARLA 版本和正常启动流程；
未来其他控制端仍可能改灯，新增校验会显式报错，不能替代唯一动作执行者的协作约定。
现有实验启动命令无需改变；需要改变 TM 种子时在控制器启动命令加 --tm-seed，不能在生成器中重设。
